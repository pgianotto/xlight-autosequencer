OpenSpec design · mcp-tool-server

Design: MCP tool server

Give a remote Claude client typed tool access to the existing xLightsAI pipeline — library, analysis, song story, themes/effects/variants, sequence generation, layout — over MCP's Streamable HTTP transport, served from the same Flask process already running at http://<nas-host>:5173 on the Synology. Every tool is a thin wrapper around an existing function; no analysis, generation, or export logic is reimplemented.

Approach

Piece 1

Pin the real mcp 2.x API

Installed mcp fresh in a scratch venv rather than assuming the 1.x FastMCP shape. Confirmed version 2.2.0:

from mcp.server.mcpserver import MCPServer

mcp = MCPServer(name="xonset", version="0.1.0")

@mcp.tool()
async def list_library() -> dict:
    """List songs in the library, with folders and staleness info."""
    ...

mcp.server.fastmcp is not silently gone — importing it raises ModuleNotFoundError with a message pointing at the rename (mcp/server/fastmcp.py is a 7-line shim that exists only to produce that error). pyproject.toml pins mcp>=2.2,<3.

Piece 2

Merge Flask (WSGI) and MCPServer (ASGI) into one process

MCPServer.streamable_http_app() returns a Starlette app — ASGI, not WSGI. Flask's app.run(...) in src/cli/review.py:187 (and its two sibling call sites in the same file) is replaced by a single ASGI launch:

from asgiref.wsgi import WsgiToAsgi
from starlette.applications import Starlette
from starlette.routing import Mount

flask_app = create_app(...)          # unchanged
mcp_app = mcp.streamable_http_app()  # /mcp handled internally

asgi_app = Starlette(routes=[
    Mount("/mcp", app=mcp_app),
    Mount("/", app=WsgiToAsgi(flask_app)),
])

import uvicorn
uvicorn.run(asgi_app, host=review_host, port=5173)

Route order matters — /mcp must be mounted before the catch-all / Flask mount or Starlette never reaches it.

Piece 3 · the real risk

SSE under uvicorn + WsgiToAsgi

This app leans on long-lived Server-Sent-Event streams for progress (/api/v1/songs/<id>/analyze/status, /api/v1/songs/<id>/export/status, legacy /progress), all implemented as Flask generator responses with stream_with_context. WsgiToAsgi supports streaming WSGI responses, but the concurrency model changes: Flask's own dev server needed threaded=True for exactly this reason (see Historical echoes) — under uvicorn, the equivalent knob is running enough worker threads/tasks that one open SSE stream doesn't starve other requests. Mitigation: explicit test (tests/integration/test_mcp_asgi_sse.py) that opens an SSE stream and, while it's open, makes a second unrelated request (e.g. GET /api/v1/library) and asserts it doesn't block behind the stream. This is exactly the failure mode 624214c fixed once already; it must not regress silently under a different server.

Piece 4

Tool implementations stay in src/review/mcp_server.py, thin

Each tool function imports and calls the same helper the corresponding api/v1 route calls (see tool surface). No route re-implements request parsing that already exists — where a route function itself contains the logic inline (e.g. export.py::start_export), the tool extracts the same call sequence rather than making an HTTP self-request, since both processes are already in the same Python process/import space.

Alternative considered

Run the MCP server as a second lightweight process on its own port (e.g. 8765), started via a new xlight-mcp entry point, alongside the unmodified Flask process. Rejected per explicit user decision: fewer moving parts to keep alive beats avoiding the WSGI/ASGI bridge, and the user wants it "integrated into the x-onset software" rather than bolted on as a sibling process. Recorded here because it's the safer option from a pure blast-radius standpoint — if the SSE-under-uvicorn risk above proves hard to resolve cleanly, this is the fallback.

Regression surface

app.run(...) in src/cli/review.py is called from three branches of review_cmd (no-arg / directory / file-or-JSON). Grepped src/ and tests/ for other create_app( + .run( pairs — none found; src/review/cli.py's own main() (the separate xlight-review entry point, port 5000, unaffected by this change) is the only other caller of create_app, and is out of scope since it's a different deployment (see proposal.md). Existing tests under tests/review/ that exercise routes directly via Flask's test client are unaffected — they don't go through app.run/uvicorn at all.

Historical echoes

Scanned .wolf/buglog.json and .wolf/cerebrum.md Do-Not-Repeat for entries touching src/cli/review.py, server.py, or SSE/threading. One direct match: commit 624214c, "Enable threaded Flask dev server — single-threaded server was blocking new requests during analysis" (also documented inline in src/cli/review.py's comments). The failure mode: a long-lived SSE analysis-progress stream held the dev server's one worker thread for the entire analysis run, so a concurrent file upload silently queued behind it until the browser gave up ("failed to fetch"). This change swaps the serving stack under the same routes, so the same class of bug is directly in scope again under different mechanics — addressed by the explicit SSE-under-uvicorn test in Piece 3 rather than assumed away.

Out of scope

  • Any new analysis, generation, or export capability. Every tool reads or triggers something the app can already do through the UI/CLI.
  • Auth/access control on the MCP endpoint. This is a single-user local-network server today (same trust model as the existing CORS policy in server.py, which reflects any Origin) — if the Synology is ever exposed past the LAN, that's a separate change.
  • Wiring the legacy hash-keyed routes (/upload, /analysis, /library, etc.) or src/review/generate_routes.py into MCP tools. They back a different, older deployment mode (see proposal.md) and aren't part of the live x-onset dashboard's data model.
  • Migrating xlight-review's (port 5000) launch mechanism. Untouched.
