OpenSpec design · segmentino-label-extraction

Design: segmentino label extraction fix

Segmentino's Vamp wrapper collects the plugin's default output instead of explicitly selecting the labelled-segmentation output every sibling Vamp wrapper in this codebase selects — silently degrading section-role classification to a weak energy-only fallback on every song it affects. Fix the extraction, add a warning when it happens again, and cap how much a single merge pass can collapse regardless of root cause.

The evidence trail

Diagnosed against a real song already in the user's library, not a synthetic case — e0f7a3435bd3296c, "It's the Most Wonderful Time of the Year" (Andy Williams, 152.6s), currently showing 3 sections on the Theme screen, one spanning 0–126.2s — 83% of the song.

1

Raw boundaries are fine

hierarchy["sections"] (8 marks): 163ms, 9601ms, 48948ms, 70031ms, 77380ms, 114892ms, 126212ms, 140214ms — evenly spaced, structurally plausible. Not the problem.

2

Every mark has label: null

algorithms_run confirms segmentino executed. Its marks carry no group label anyway — result.py's _mark_to_dict (line 658) omits any key whose value is None, which is why the JSON shows no "label" key at all rather than "label": null literally.

3

Root cause: the one Vamp wrapper missing output=

Every multi-output-capable Vamp wrapper in src/analyzer/algorithms/ explicitly selects an output:

Wrappervamp.collect(..., output=?)
vamp_beats.pyexplicit self.vamp_output
vamp_onsets.pyexplicit self.vamp_output
vamp_pitch.pyexplicit self.vamp_output
vamp_harmony.py (chordino — labels work today)explicit self.vamp_output
vamp_structure.py (QM segmenter, the sibling structural segmenter)vamp_output = "segmentation"
vamp_segmentation.py (segmentino)— none. Relies on Vamp's default output.

A multi-output plugin's default output is not guaranteed to be the semantically useful one. Segmentino, whose entire purpose is producing labelled structural groups, is the one wrapper not asking for it by name.

4

Downstream: silent fallback to the weak path

src/story/builder.py's _dominant_label() (line 229) finds no candidates for any segment when boundary_label is empty, so every section_labels entry passed to classify_section_roles() is None — this forces the energy-percentile-only heuristic path (section_classifier.py) instead of the label-aware _classify_by_labels() path, for every song this bug affects, not just the diagnosed one.

5

Collapse: the exact pattern already logged once, on a different song

On this song's fairly uniform dynamics, 6 of 8 segments fell below the chorus energy threshold → all labelled verse → builder.py's consecutive-same-role merge (Step 4b) glued them into one block. docs/segment-classification-changelog.md's 2026-03-31 entry documents this identical failure mode on Ghostbusters ("93-second s09 'verse'... swallowed 6 sections... the consecutive-same-role merger collapsed too aggressively when the heuristic got the base labels wrong"). Same mechanism, different trigger, reproducing live.

Approach

Piece 1 · needs live verification first

Explicit output selection in vamp_segmentation.py

Add vamp_output = "segmentation" (matching QM segmenter's convention — the most likely value, since both are C4DM-family structural segmenters) and pass output=self.vamp_output to vamp.collect(). Before writing this as final, confirm the real output ID: vamp.list_outputs_of("segmentino:segmentino") in the Linux dev container (this machine has no vamp host library to check directly). If the real ID differs from "segmentation", use that instead — do not ship a guess.

Piece 2

Warn when segmentino runs but yields zero labels

In the orchestrator's L1 structure stage (around orchestrator.py:485-501), after building sections, check whether segmentino contributed any labelled marks; if it ran but every mark's label is None, append to result.warnings (the existing mechanism, already surfaced in the UI). Makes a future regression on this exact code path visible immediately instead of silently degrading section quality the way this one did for an unknown length of time.

Piece 3 · defense in depth

Cap the consecutive-merge collapse

In builder.py Step 4b, before extending a merged run's end_ms, check whether doing so would push the merged section's duration past a fixed fraction of duration_ms (proposed: 50%). If so, don't merge — keep the sections separate even though they share a role. Same spirit as the existing _genius_quality_ok() gate ("reject if any single section covers >60% of song duration"), applied at the point the collapse actually happens rather than as an after-the-fact quality gate on a data source (Genius) that no longer exists in this pipeline. This piece ships regardless of whether Piece 1's exact output ID guess is right on the first try — it's independent insurance against the same collapse from a different trigger in the future.

Alternative considered

Fix only the downstream cap (Piece 3) and skip investigating the Vamp extraction bug, treating segmentino's missing labels as an unfixable upstream fact of life. Rejected: it would cap the damage but leave every affected song permanently on the weaker energy-only classification path, when the actual fix is a one-line wrapper change once the correct output ID is confirmed. Piece 3 stays in scope anyway as genuine defense in depth, but it's not a substitute for Piece 1.

Files touched

  • Modified: src/analyzer/algorithms/vamp_segmentation.py (add explicit output selection), src/analyzer/orchestrator.py (label-loss warning), src/story/builder.py (Step 4b merge cap), docs/segment-classification-changelog.md (mandatory entry, appended not edited)
  • Unmodified: src/analyzer/boundary_cluster.py, src/story/section_classifier.py, src/story/section_merger.py, src/story/boundary_refinement.py — correctly out of scope per the alternative considered above; each is a real, separate follow-up once this stops masking whether they're the next weakest link.

Regression surface

SegmentinoAlgorithm has exactly one caller (orchestrator.py's algorithm registry, via registry.py:50) — grepped src/ and tests/, no direct instantiation elsewhere. The Step 4b merge cap changes behavior for every song's role-classification merge, not just segmentino-affected ones — a song that legitimately has 6 genuinely same-role consecutive sections spanning >50% of its length (e.g. a long ambient drone track that's musically almost entirely "verse") would now stay split instead of merging. Existing tests for section_classifier.py / builder.py must be re-run to catch this; a new test fixture specifically exercising the cap (deliberately uniform-energy synthetic audio, matching this repo's existing fixture-generation conventions in tests/conftest.py) is part of this change.

Cache invalidation: per the 2026-07-25 changelog entry's own documented lesson ("bug-265 lesson repeated"), a plain "Reanalyze" passes fresh=False and will keep re-serving cached _hierarchy.json/_story.json results with the old, unlabelled sections unless the hierarchy schema version is bumped to force invalidation. Bumping SCHEMA_VERSION is in scope for this change for exactly that reason.

Historical echoes

Read docs/segment-classification-changelog.md in full (mandatory per CLAUDE.md) before writing this design. Two direct matches:

  • 2026-03-31, "Label-aware classifier + consecutive merge" — the exact collapse mechanism (consecutive same-role sections merging too aggressively when base labels are wrong), on Ghostbusters. That entry's own root cause was different (energy-threshold miscalibration, not missing Vamp labels), but the failure shape is identical — strong evidence the merge step itself has always been under-guarded against a total-labeling failure, independent of what triggers it.
  • 2026-07-25, "demucs/madmom sidecar bug collapsed every song to one flat section" — a different root cause (in-process import vs. sidecar subprocess) producing the same symptom class (silent upstream data loss → degraded/collapsed sections downstream). Confirms this class of bug (upstream analyzer output silently empty/wrong, section builder has no guard against acting on it) has happened at least twice before under different mechanisms — Piece 2 (the warning) and Piece 3 (the cap) are specifically aimed at making the next instance of this bug class visible and bounded rather than silent and unbounded.

No entry found addressing the Vamp output= selection issue itself — this appears to be a genuinely new finding, not a repeat of a previously-diagnosed-and-reverted attempt.

Out of scope

  • section_classifier.py's energy-threshold tuning (top-25%-energy = chorus) — a real, separate follow-up once labels are flowing correctly and it's possible to tell whether the thresholds themselves are still the next weakest link.
  • Using boundary_cluster.py's agreement scores to drive merge decisions instead of just scoring them after the fact — a distinct, larger change to how two modules interact, proposed separately.
  • Any change to boundary_refinement.py's three lyric-anchored fixes — unaffected by this bug (they operate on already-classified sections' text content, not the label-loss issue).
